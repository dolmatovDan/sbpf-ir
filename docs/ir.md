# IR

Формат, в котором лифтер отдаёт программу символьной машине (Kotlin, на базе usvm). Документ — контракт между проектами: любое несовместимое изменение повышает `format_version`.

Версии sBPF: только v0 и v3. Все различия между ними лифтер устраняет, поэтому семантика IR от версии не зависит. Исключение — расположение памяти: это забота модели памяти на стороне Kotlin.

## Принципы

- **Одна инструкция sBPF — один statement** (или один выход блока, см. ниже). Единственное исключение — `check`: он стоит перед инструкцией, которая может упасть, и имеет тот же `pc`. Шаг usvm соответствует инструкции, `pc` есть у каждого statement'а.
- **Выражения — деревья** битвекторных операций, которые один к одному переводятся в термы KSMT. Временных переменных и SSA нет: регистры `r0`–`r10` — изменяемые 64-битные переменные.
- **Неявного нет.** Ширина, знаковость, расширение, маска сдвига, знаковое расширение констант, проверка деления записаны явно. Если для операции IR нужно знать особенность sBPF, это ошибка лифтера.
- **Переходов `goto` нет.** Передача управления описывается выходом блока, а блоки ссылаются друг на друга по `pc`.
- **Память — не здесь.** IR описывает чтения и записи (адрес, ширина), но не регионы, их адреса, стек, кучу, input, начальные значения `r1` и `r10`. Всё это задаёт модель памяти в Kotlin.

## Файл

JSON, верхний уровень:

```json
{
  "format_version": 1,
  "sbpf_version": 3,
  "entrypoint": 233,
  "text_vaddr": "0x100000000",
  "ro_region": { "vaddr": "0x0", "data": "<base64>" },
  "address_taken": [76, 1891],
  "functions": [ ... ]
}
```

| Поле | Смысл |
|---|---|
| `format_version` | Версия этого формата. Добавление необязательного поля версию не меняет: потребитель игнорирует незнакомые поля. |
| `sbpf_version` | `0` или `3`. Только для справки и для модели памяти. |
| `entrypoint` | `pc` точки входа (это же `entry` одной из функций). |
| `text_vaddr` | Виртуальный адрес инструкции с `pc = 0`. Нужен для `callx`. |
| `ro_region` | Read-only регион, как его отображает загрузчик `solana-sbpf` (`get_ro_region`): адрес начала и байты. В v0 код входит в этот регион, в v3 нет. |
| `address_taken` | Функции, адрес которых (`text_vaddr + 8·pc`) встречается в программе как константа `lddw` или как 8-байтное слово в `ro_region` вне кода. Кандидаты для `callx`. |
| `functions` | Функции в порядке адресов. |

64-битные значения (адреса, константы) записываются строками `"0x…"`: в JSON числа больше 2⁵³ теряют точность.

## Функции и блоки

```json
{
  "entry": 84,
  "name": "fn_84",
  "blocks": [
    { "start": 84, "noreturn": false, "statements": [ ... ], "exit": { ... } }
  ]
}
```

- Функция идентифицируется `pc` входа, блок — `pc` первой инструкции. Оба уникальны во всей программе.
- `name` — demangled-имя символа, `entrypoint` или `fn_<pc>`, если символов нет.
- Первый блок функции начинается с `entry`.
- Выход блока может вести в блок **другой** функции: компилятор иногда переходит в общий хвост чужой функции. Границы функций приблизительны (функция без символа, вызываемая только через `callx`, окажется внутри предыдущей).
- `noreturn` — подсказка: блок кончается вызовом, который по анализу не возвращается. Ребро возврата при этом сохранено.

## Выражения

Типы: битвектор ширины 8, 16, 32 или 64 и `bool`. `bool` получается только из сравнений и используется только в условиях `branch` и `check`.

Листья:

| JSON | Тип |
|---|---|
| `{"reg": 3}` | bv64, значение регистра |
| `{"const": "0x5", "w": 32}` | константа ширины `w` |

Операции записываются как `{"op": "<имя>", "args": [...]}`, у приведений ширины ещё есть `"w"`:

| Операции | Аргументы → результат | Семантика |
|---|---|---|
| `add` `sub` `mul` `and` `or` `xor` | bvN, bvN → bvN | по модулю 2ᴺ |
| `udiv` `urem` | bvN, bvN → bvN | беззнаковые; делитель ≠ 0 гарантирует `check` или верификатор |
| `shl` `lshr` `ashr` | bvN, bvN → bvN | как в SMT: сдвиг на ≥ N даёт 0 (или знак у `ashr`); маску по модулю N ставит лифтер |
| `neg` | bvN → bvN | `0 − x` |
| `bswap` | bvN → bvN | смена порядка байт, N ∈ {16, 32, 64} |
| `zext` | bvM → bv`w` | расширение нулями, `w` ≥ M |
| `trunc` | bvM → bv`w` | младшие `w` бит, `w` ≤ M |
| `eq` `ne` `ult` `ule` `ugt` `uge` `slt` `sle` `sgt` `sge` | bvN, bvN → bool | сравнения; `s…` — знаковые |

Знакового расширения (`sext`) в списке нет: в v0/v3 оно встречается только у констант, и лифтер расширяет их сам.

## Statement'ы

Каждый statement содержит `pc` своей инструкции.

| `op` | Поля | Семантика |
|---|---|---|
| `assign` | `dst`, `value` | `r[dst] := value` (bv64) |
| `load` | `dst`, `w`, `addr` | `r[dst] := zext64(память[addr .. addr+w/8))`, little-endian |
| `store` | `w`, `addr`, `value` | `память[addr .. addr+w/8) := value` (bv`w`), little-endian |
| `check` | `cond`, `error` | если `cond` ложно — путь завершается ошибкой `error` |

- `dst` ∈ 0..9: писать в `r10` верификатор не даёт.
- `addr` — bv64, сложение в нём переполняется по модулю 2⁶⁴, как в sBPF.
- Любой `load`/`store` может завершить путь ошибкой `AccessViolation`. Когда это происходит, решает модель памяти, в IR проверки нет.
- `check` не считается инструкцией. Одна инструкция = один statement, кроме `check`, или один выход блока с `pc`. По ним ведётся учёт CU.

## Выход блока

Поле `exit` описывает, куда идёт управление после последнего statement'а блока.

| `kind` | Поля | Семантика |
|---|---|---|
| `next` | `target`, `pc`? | переход в блок `target`. Без `pc` — продолжение в следующий блок, с `pc` — это инструкция `ja` (она тратит CU) |
| `branch` | `pc`, `cond`, `then`, `else` | если `cond` — в блок `then`, иначе в `else` |
| `call` | `pc`, `target`, `next` | вызов функции с входом `target`, возврат в блок `next` |
| `callx` | `pc`, `reg`, `next` | косвенный вызов по адресу из `r[reg]`, возврат в `next` |
| `syscall` | `pc`, `hash`, `name`, `next` | вызов syscall'а, продолжение в `next` |
| `return` | `pc` | инструкция `exit` |
| `trap` | `pc`, `error` | путь завершается ошибкой |

`next` у вызовов — `null`, если вызов последний в программе: возврат из него даёт `ExecutionOverrun`.

### `call` и `return`

Регистры живут в кадрах (`URegistersStack` в usvm):

- **вызов**: новый кадр — копия всех регистров вызывающего, кроме `r10`. `r10` вызванного = `r10` вызывающего + шаг кадра. Шаг (4096, в v0 с промежутками между кадрами 8192) задаёт модель памяти;
- **`return` из вызванной функции**: кадр снимается, вызывающий получает `r0`–`r5` из снятого кадра, а его `r6`–`r10` не меняются. Так ведёт себя VM: она сама сохраняет и восстанавливает `r6`–`r10`. Читать `r1`–`r5` после вызова программа может (например, второе значение, которое вернул компилятор);
- **`return` из точки входа**: программа завершается с результатом `r0`;
- превышение глубины вызовов (`CallDepthExceeded`) проверяет Kotlin.

### `callx`

Цель вычисляется во время исполнения:

```
pc цели = (r[reg] − text_vaddr) / 8          // по модулю 2⁶⁴, деление с округлением вниз
```

- если `pc` цели за концом кода — ошибка `CallOutsideTextSegment` (кадр к этому моменту уже положен, поэтому `CallDepthExceeded` проверяется раньше);
- цель может быть любой инструкцией, не обязательно началом функции, а невыровненный адрес молча округляется.

Рекомендуемая обработка в машине: если значение регистра символьное, разветвиться по функциям из `address_taken` с условием `r[reg] = text_vaddr + 8·entry`, а для всех остальных значений завести путь с ошибкой «вызов не по известной функции».

### `syscall`

`hash` — ключ syscall'а в реестре (поле `imm` инструкции), `name` — имя из списка syscall'ов agave или `null`, если хеш неизвестен. В v0 под `name: null` попадает и `call`, цель которого не нашлась в реестре программы: отличить его от неизвестного syscall'а нельзя.

Syscall читает `r1`–`r5` и пишет `r0`. Остальные регистры не меняются. Действие на память и ошибки описывает модель syscall'а в Kotlin по имени.

## Ошибки

| Ошибка | Где |
|---|---|
| `DivideByZero` | явно, `check` перед `udiv`/`urem` с регистром-делителем |
| `UnsupportedInstruction` | явно, `trap` на `call`, цель которого не разрешается (в v3 `src` не 0/1, или цель не начало инструкции) |
| `ExecutionOverrun` | явно, `trap` после последней инструкции программы, если управление проваливается за конец кода |
| `AccessViolation` | Kotlin, модель памяти |
| `CallDepthExceeded` | Kotlin |
| `CallOutsideTextSegment` | Kotlin, при разборе цели `callx` |
| исчерпание CU | Kotlin |
| ошибки syscall'ов | Kotlin, модели syscall'ов |

Верификатор `solana-sbpf` гарантирует, и IR на это опирается: константа сдвига меньше ширины; делитель-константа не 0; цели переходов внутри кода и не во второй слот `lddw`; `r10` не записывается; аргумент `le`/`be` — 16, 32 или 64; регистр `callx` допустимый.

## Перевод инструкций

Обозначения: `d`, `s` — регистры `dst` и `src`; `imm` — 32-битная константа инструкции; `off` — 16-битное смещение; `ext(x)` — знаковое расширение константы до 64 бит, вычисленное лифтером; `lo32(x)` — `{"op": "trunc", "w": 32, ...}`.

**64-битная арифметика.** Константа всегда знаково расширяется: `add64 r1, -1` прибавляет `0xffffffffffffffff`.

| sBPF | IR |
|---|---|
| `add64 d, imm` (и `sub`, `mul`, `and`, `or`, `xor`) | `d := add(d, ext(imm))` |
| `add64 d, s` | `d := add(d, s)` |
| `div64 d, imm` / `mod64 d, imm` | `d := udiv(d, ext(imm))` / `urem` |
| `div64 d, s` / `mod64 d, s` | `check ne(s, 0) DivideByZero`; `d := udiv(d, s)` / `urem` |
| `lsh64 d, imm` (и `rsh64`, `arsh64`) | `d := shl(d, imm)` / `lshr` / `ashr` |
| `lsh64 d, s` | `d := shl(d, and(s, 63))` |
| `neg64 d` | `d := neg(d)` |
| `mov64 d, imm` / `mov64 d, s` | `d := ext(imm)` / `d := s` |
| `lddw d, imm64` | `d := imm64`, инструкция занимает 2 слота |

**32-битная арифметика.** Считается в 32 битах, результат всегда расширяется нулями (знаковое расширение результата есть только в v2). Константа — младшие 32 бита `imm`.

| sBPF | IR |
|---|---|
| `add32 d, imm` (и `sub`, `mul`, `and`, `or`, `xor`) | `d := zext64(add(lo32(d), imm₃₂))` |
| `div32 d, s` / `mod32 d, s` | `check ne(lo32(s), 0) DivideByZero`; `d := zext64(udiv(lo32(d), lo32(s)))` / `urem` |
| `lsh32 d, s` (и `rsh32`, `arsh32`) | `d := zext64(shl(lo32(d), and(lo32(s), 31)))` |
| `neg32 d` | `d := zext64(neg(lo32(d)))` |
| `mov32 d, imm` / `mov32 d, s` | `d := zext64(imm₃₂)` / `d := zext64(lo32(s))` |

**Порядок байт.**

| sBPF | IR |
|---|---|
| `le16` / `le32` | `d := zext64(trunc16(d))` / `zext64(lo32(d))` |
| `le64` | ничего не меняет, `d := d` |
| `be16` / `be32` | `d := zext64(bswap(trunc16(d)))` / `zext64(bswap(lo32(d)))` |
| `be64` | `d := bswap(d)` |

**Память.** Адрес — `add(reg, ext(off))`.

| sBPF | IR |
|---|---|
| `ldx{b,h,w,dw} d, [s+off]` | `load d, w, add(s, ext(off))` |
| `stx{b,h,w,dw} [d+off], s` | `store w, add(d, ext(off)), trunc_w(s)` |
| `st{b,h,w,dw} [d+off], imm` | `store w, add(d, ext(off)), младшие w бит ext(imm)` |

**Переходы.** У 64-битных сравнений с константой она знаково расширяется. `jmp32` (только v3) сравнивает `lo32` регистров с младшими 32 битами `imm`.

| sBPF | Условие `branch` |
|---|---|
| `jeq` `jne` | `eq` `ne` |
| `jgt` `jge` `jlt` `jle` | `ugt` `uge` `ult` `ule` |
| `jsgt` `jsge` `jslt` `jsle` | `sgt` `sge` `slt` `sle` |
| `jset` | `ne(and(a, b), 0)` |
| `ja` | выход `next` с `pc` |

**Вызовы.** `call` к функции — выход `call`; к syscall'у — `syscall`; неразрешимый — `trap UnsupportedInstruction`. `callx` — выход `callx`: регистр в v0 берётся из `imm`, в v3 из `dst`. `exit` — выход `return`.

## Пример

Функция `checked_div` из `tests/programs/native-basic` (v3):

```
84: jeq r3, 0, +5
85: div64 r2, r3
86: stxdw [r1+0x8], r2
87: mov64 r2, 0
88: stxw [r1+0x0], r2
89: exit
90: stw [r1+0x4], 23
91: mov64 r2, 1
92: ja -5
```

Текстовая запись IR (для чтения человеком):

```
fn_84:
  bb_84:
    [84] branch eq(r3, 0) → bb_90, bb_85
  bb_85:
    [85] check ne(r3, 0) DivideByZero
    [85] r2 := udiv(r2, r3)
    [86] store.64 add(r1, 8), r2
    [87] r2 := 0
    → bb_88
  bb_88:
    [88] store.32 add(r1, 0), trunc32(r2)
    [89] return
  bb_90:
    [90] store.32 add(r1, 4), 23:32
    [91] r2 := 1
    [92] next → bb_88
```

Блок `bb_85` в JSON:

```json
{
  "start": 85,
  "noreturn": false,
  "statements": [
    { "pc": 85, "op": "check", "error": "DivideByZero",
      "cond": { "op": "ne", "args": [{ "reg": 3 }, { "const": "0x0", "w": 64 }] } },
    { "pc": 85, "op": "assign", "dst": 2,
      "value": { "op": "udiv", "args": [{ "reg": 2 }, { "reg": 3 }] } },
    { "pc": 86, "op": "store", "w": 64,
      "addr": { "op": "add", "args": [{ "reg": 1 }, { "const": "0x8", "w": 64 }] },
      "value": { "reg": 2 } },
    { "pc": 87, "op": "assign", "dst": 2, "value": { "const": "0x0", "w": 64 } }
  ],
  "exit": { "kind": "next", "target": 88 }
}
```
