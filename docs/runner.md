# Конкретный раннер

`sbpf-lift run <example.json> [--registers] [--trace] [-o out.json]` исполняет одну инструкцию контракта так, как её исполнил бы валидатор agave 4.3: загрузка `.so`, сериализация аккаунтов, syscall'ы, CPI, учёт CU. Исполнение идёт через [Mollusk](https://github.com/anza-xyz/mollusk) (`mollusk-svm 0.16.1`), библиотеку `crates/sbpf-run`.

Назначение — эталон для тестов. Символьная машина подбирает входные данные, раннер исполняет на них контракт по-настоящему, результаты сравниваются. Формат ниже — контракт с Kotlin-стороной, как и `docs/ir.md`: изменения согласуются.

## Пример (вход)

```json
{
  "program": "../../programs/bin/native-cpi.v0.so",
  "program_id": "Cpi1111111111111111111111111111111111111111",
  "programs": [{ "program_id": "...", "program": "other.so" }],
  "instruction_data": "00a086010000000000",
  "accounts": [
    { "key": "A1ice11111111111111111111111111111111111111", "owner": "11111111111111111111111111111111",
      "lamports": 2000000, "data": "", "is_signer": true, "is_writable": true },
    { "key": "11111111111111111111111111111111", "owner": "NativeLoader1111111111111111111111111111111",
      "lamports": 1, "executable": true }
  ]
}
```

| Поле | Обяз. | Смысл |
|---|---|---|
| `program` | да | путь к `.so` относительно файла примера |
| `program_id` | да | адрес программы, base58 |
| `programs` | нет | дополнительные программы-цели CPI: `program_id` и путь к `.so`. `program_id` не может совпадать с основной программой, встроенной программой или другим элементом `programs` |
| `instruction_data` | да | данные инструкции, hex |
| `accounts` | нет | аккаунты инструкции в порядке передачи программе |
| `compute_unit_limit` | нет | лимит CU; по умолчанию 200 000, как у транзакции без ComputeBudget; больше 1 400 000 урезается |

Аккаунт: `key`, `owner` (base58), `lamports` — обязательны; `data` (hex, по умолчанию пусто), `executable`, `is_signer`, `is_writable` (по умолчанию `false`), `rent_epoch` (по умолчанию `u64::MAX`, как у новых аккаунтов в мейннете; программа видит его в сериализованном входе). Неизвестные поля — ошибка.

- Каждый элемент `accounts` — один `AccountMeta` инструкции. Повтор ключа означает тот же аккаунт: флаги `is_signer`/`is_writable` у повторов могут отличаться, остальное состояние должно совпадать, иначе ошибка входа.
- Аккаунт программы (`program_id`) передавать не нужно. Программу-цель CPI нужно передать в `accounts`, как это делает настоящая транзакция. Встроенные программы (System Program, загрузчики BPF v1–v3) уже есть, их аккаунт — `owner = NativeLoader1111111111111111111111111111111`, `executable = true`.
- Программы загружаются под upgradeable-загрузчик (`BPFLoaderUpgradeab1e11111111111111111111111`). Версия sBPF (v0/v3) берётся из ELF.

## Результат (выход)

| Поле | Смысл |
|---|---|
| `status` | `success` или `failure` |
| `error` | только при `failure`: `InstructionError` в виде `Debug` — `InvalidInstructionData`, `Custom(6000)`, `ProgramFailedToComplete` (в том числе превышение лимита CU)… Если инструкция прошла, но оставила аккаунт в недопустимом для ренты состоянии, — `InsufficientFundsForRent`: валидатор откатил бы такую транзакцию |
| `compute_units` | израсходованные CU, включая CPI |
| `return_data` | данные `sol_set_return_data`, hex |
| `accounts` | аккаунты после исполнения: `key`, `owner`, `lamports`, `data` (hex), `executable`; без повторов, в порядке первого вхождения. При `failure` — исходные |
| `logs` | логи рантайма, как в транзакции: `Program … invoke [1]`, `Program log: …`, `Program … consumed …` |
| `registers` | только с `--registers`: последняя запись трассы; `null`, если VM верхнего уровня не исполнила ни одной инструкции |
| `trace` | только с `--trace`: регистры перед каждой исполненной инструкцией программы верхнего уровня (может быть `[]`) |

Все числа — беззнаковые u64 JSON-числами, без кавычек. Регистры часто больше 2⁶³ (`-1` — это `18446744073709551615`), поэтому в Kotlin их нужно читать как `ULong` (kotlinx.serialization это поддерживает), а не `Long`. jq и JavaScript теряют точность на числах больше 2⁵³.

Запись трассы — 12 чисел: `r0`…`r10` и номер слота инструкции (`pc`, 8-байтные слоты от начала `.text`). Записывается состояние **перед** инструкцией, поэтому последняя запись — состояние на последней исполненной инструкции: при успехе это `exit` верхней функции, и `r0 = 0`; при ошибке — инструкция или syscall, на котором исполнение остановилось.

Инструкции программ, вызванных через CPI, в трассу не попадают (берётся только трасса вызова с `stack_height = 1`). Тестами это пока не проверено: в тестовых контрактах CPI идёт только во встроенную System Program, у которой нет трассы VM.

Ошибки входа (нет файла, плохой hex или base58, путь не на `.so`, паника Mollusk) — сообщение в stderr и код выхода 1. Ошибка контракта — это `status: failure`, код выхода 0.

## Отличия от мейннета

- Набор фич — `SVMFeatureSet::all_enabled()` из Mollusk, а не текущий набор мейннета. Активированы, например, все syscall'ы, которые в мейннете ещё за фичами.
- Sysvar'ы (`Clock`, `Rent`, …) — значения Mollusk по умолчанию.
- Исполняется одна инструкция, а не транзакция: комиссия с плательщика не списывается, подписи не проверяются (`is_signer` задаётся прямо).
- На x86_64 (кроме Windows) программа исполняется JIT'ом, иначе — интерпретатором `solana-sbpf`, как и у валидатора.

## Тестовые примеры

`tests/examples/<контракт>/*.json` генерирует `tests/examples/gen.py`. Все примеры указывают на `.v0.so`; тесты `crates/sbpf-run/tests/run.rs` исполняют их и на `.v3.so` и проверяют, что итог совпадает (кроме CU).
